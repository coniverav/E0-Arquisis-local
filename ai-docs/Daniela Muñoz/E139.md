# E1-39 — Request de información faltante

## Uso de IA

Se utilizó IA como apoyo para analizar el flujo definido para E1-39 y proponer una implementación consistente con la arquitectura existente del proyecto.

La asistencia se utilizó principalmente para:

- Revisar el mecanismo existente de persistencia y publicación de mensajes salientes.
- Diseñar la generación persistente de mensajes `request` utilizando el outbox existente.
- Implementar la detección automática de un `status-statement` faltante cuando llega un mensaje asociado a un ciclo sin estado inicial.
- Mantener la publicación RabbitMQ aislada en el connector.
- Incorporar la correlación entre una solicitud publicada y la respuesta posterior recibida desde la central.
- Incorporar soporte para solicitudes de `status-statement` y `distance-table`.
- Agregar pruebas de creación, deduplicación, despacho, publicación, correlación y solicitud automática.
- Revisar errores de integración e indentación detectados durante las pruebas.

La implementación fue revisada y ejecutada localmente.

## Prompts relevantes

Los siguientes prompts resumen las consultas realizadas durante el desarrollo de la tarjeta.

### Prompt 1 — Diseño del request faltante

> Implementemos E1-39. Revisa el enunciado y la arquitectura existente para permitir que el nodo solicite información faltante mediante mensajes `request`.

### Prompt 2 — Reutilización del outbox

> Quiero reutilizar el `OutboundMessage` y el outbox existente para persistir los requests antes de publicarlos. Mantén RabbitMQ aislado en el connector y evita agregar acceso directo al broker desde master.

### Prompt 3 — Requests directos

> Revisa el protocolo de peticiones directas. Los mensajes `request` para `status-statement` y `distance-table` no deben inventar un `cycleId`.

### Prompt 4 — Correlación de respuesta

> Diseña una forma de correlacionar un request pendiente con la respuesta posterior de la central y registrar `response_msg_id`, `response_idpk` y el momento de resolución.

### Prompt 5 — Solicitud automática de status

> Cuando llegue un mensaje asociado a un ciclo que todavía no tenga `status-statement`, quiero que el backend genere automáticamente un request de estado sin crear solicitudes duplicadas.

### Prompt 6 — Validación

> Diseña pruebas para creación, deduplicación, despacho, publicación, correlación y solicitud automática. Luego revisa la suite completa del master y del connector antes de cerrar la tarjeta.
